# Kerben Travel: ручное обновление backend

GitHub Actions запускает только проверки и тесты; он не отправляет код и не запускает серверную сборку.
Ручная команда отправляет текущие сохранённые файлы проекта, включая изменения без commit.

## Запуск

Откройте PowerShell в папке `C:\Users\user\Kyrgyz_Go` и выполните:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\deploy.ps1
```

Сначала выполняется `python -m scripts.run_tests -q`. Нужен работающий Docker Desktop/Compose либо явно заданный `TEST_DATABASE_URL` для выделенного PostgreSQL с правом `CREATEDB`. Если тесты завершились ошибкой, загрузка не начинается. Затем передаются исходники; сервер проверяет ревизию БД, наличие места и резервное копирование, собирает образ и перезапускает только backend. Успех обозначается сообщением `DEPLOYMENT SUCCEEDED`.

Приложение доступно по адресу, заданному серверным `API_DOMAIN`. Пока идёт команда, не закрывайте терминал.

## Проверить доступ без обновления

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\deploy.ps1 -Check
```

Этот режим проверяет упаковку файлов, SSH, наличие серверного deploy-скрипта и здоровый backend. Он не загружает архив на сервер, не применяет миграции и не перезапускает приложение. Успех: `CHECK PASSED`. Проверка сама по себе не гарантирует, что будущая сборка пройдёт: место на диске и зависимости повторно проверяются сервером при настоящем обновлении.

## Ключ и Python

По умолчанию используется личный ключ `C:\Users\user\.ssh\kyrgyzgo_ec2_deploy`. Он не передаётся на сервер или в архив. GitHub Actions Secrets для этой команды не нужны.

Для другого личного ключа:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\deploy.ps1 -KeyPath "$env:USERPROFILE\.ssh\my_server_key"
```

Для Python из подготовленного окружения добавьте `-PythonExecutable "C:\path\to\python.exe"`. Нужен Python 3.12 или новее, зависимости проекта и тестовые пакеты:

```powershell
python -m pip install -r requirements-dev.txt httpx websockets
```

Флаг `-SkipTests` пропускает только локальные тесты. Используйте его осознанно, если эту самую версию уже проверили; проверки и резервная копия на сервере остаются обязательными.

`ExecutionPolicy Bypass` действует только для этого запуска PowerShell и не меняет общую политику компьютера.

## Что отправляется

- Только `main.py`, `create_admin.py`, `requirements.txt`, `Dockerfile`, `.dockerignore`, `alembic.ini` и каталоги `ML`, `mysite`, `alembic`, `scripts`.
- Локальные `.env`, ключи, резервные копии баз данных, кеши, документация, Git и виртуальные окружения не отправляются. Символические ссылки в исходниках запрещены.
- Файлы берутся с диска, поэтому сначала сохраните изменения в редакторе. Изменения в серверных Compose, Caddy и `.env` этой командой не устанавливаются.
- Ручной релиз идентифицируется первыми 40 символами SHA-256 архива; это идентификатор снимка, не Git commit. Он записывается в серверный `deployment-state.json` как `revision`.

## Безопасность и ограничения

Эта инструкция описывает отправку исходников и не устанавливает доверенную точку входа `/usr/local/lib/kyrgyzgo/ci_deploy.py`, серверные Compose-файлы или `.env`. Архив приложения не обновляет эту отдельную серверную точку входа: перед использованием проверьте, что установленная на сервере версия совместима с актуальным `scripts/ci_deploy.py` и включает каталог `ML`. Серверный deploy-скрипт сравнивает схему БД с кандидатом и останавливается с `migration_required`, если версии различаются. Перед миграцией сделайте резервную копию, проверьте текущую ревизию БД и примените миграции из той же версии исходников, что собираетесь развернуть. Текущая вершина исходного дерева — `20261107_0024`; миграции `20261103_0021` и `20261107_0024` добавляют отзывы о турах и клиентские заявки. Состояние production-БД этой инструкцией не подтверждается. Старые сообщения миграция `20261029_0017` сохраняет с `reply_to_message_id=NULL`.

- Проверяется заранее доверенный SSH-ключ сервера. При его смене команда остановится: не отключайте проверку, сначала выясните причину.
- Используется уже установленный доверенный `/usr/local/lib/kyrgyzgo/ci_deploy.py`. Скрипт с компьютера не подменяет эту серверную точку входа.
- Серверная точка входа не обновляется вместе с архивом. Администратор сервера должен отдельно установить и сверить её версию с репозиторием; эта команда проверяет и передаёт только локальный кандидат.
- Если зависимости и Dockerfile не менялись, сохраняется проверенный серверный runtime. Для полной сборки с изменёнными зависимостями нужно минимум 2 GiB свободного места. При свободном месте менее 256 MiB запрещено любое обновление.
- При ошибке сборки прежний backend продолжает работать. При ошибке запуска выполняется откат образа. Применённые миграции автоматически не откатываются; делайте их обратно совместимыми.
- Резервные копии находятся в `/home/ubuntu/kyrgyzgo-backups/ci-*`, исходники — `/home/ubuntu/releases/ci-*`. Автоматического удаления копий или Docker volumes нет.
- Команде выдаются отдельные личные SSH-ключи с обычным серверным доступом. Не пересылайте общий приватный ключ. Ограниченный ключ GitHub Actions не подходит для этой команды проверки.
- Перед обновлением согласуйте изменения с командой. Блокировка предотвращает одновременный перезапуск, но не защищает от последующей загрузки устаревшей версии коллегой. GitHub Actions может выполнять production-деплой только после отдельного включения, описанного в [инструкции автодеплоя](automatic-deployment.md); по умолчанию он выключен.

Для будущего перехода на другой сервер Python-команда принимает `--host ubuntu@hostname`
и обязательный `--known-hosts path/to/verified_known_hosts`. Старый встроенный ключ
нельзя использовать для нового адреса. Проверка `--check` тоже подключается по SSH:
при запрете на работу с сервером её не запускают. В текущей задаче выполняются
только локальные тесты, без `--check` и без отправки архивов.


Current migration sequence includes `20261107_0023` (administrator MFA and roles) and `20261107_0024` (persistent translation jobs). Apply migrations during maintenance; enroll each active administrator with `python -m scripts.enroll_admin_mfa <username>` before reopening admin access.
