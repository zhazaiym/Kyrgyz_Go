# Воспроизводимый запуск тестов

## Цель

Сделать один безопасный и понятный способ запустить полный набор тестов проекта на Windows, Linux и в GitHub Actions. Тесты должны всегда работать с явно заданной тестовой PostgreSQL и не должны случайно брать адрес рабочей базы из `.env`.

## Текущее состояние

- `tests/conftest.py` поднимает отдельную временную БД через `tests/postgres_support.py` до сбора тестов.
- `tests/postgres_support.py` сейчас может брать URL из `TEST_DATABASE_URL`, `DATABASE_URL` или `.env`. Последние два источника могут неожиданно направить тестовый запуск на рабочую БД.
- Workflow CI уже поднимает PostgreSQL 17, запускает проверки синтаксиса, Ruff, форматирования, аудит зависимостей, Bandit, ML-тесты и полный набор.
- На Windows локальная команда `pytest` зависит от Docker и DNS-имени `host.docker.internal`; если Docker не запущен, тесты падают ещё до сбора.

## Дизайн

Добавить единый запускатель `python -m scripts.run_tests`. Если задан `TEST_DATABASE_URL`, запускатель использует его. Иначе он поднимает отдельный временный PostgreSQL через `docker compose -f docker-compose.test.yml`, ждёт readiness, задаёт тестовый URL дочернему процессу pytest и гарантированно удаляет контейнер после завершения. Compose не использует постоянные volumes. Временная БД, которую создаёт тестовая фикстура, остаётся отдельной от контейнерной базовой БД.

`tests/postgres_support.py` будет принимать только `TEST_DATABASE_URL` и завершаться понятной ошибкой, если переменная отсутствует или URL не PostgreSQL. В `.env` и `DATABASE_URL` больше не будет резервного чтения для тестов. Это исключает неявное подключение тестов к приложению.

GitHub Actions сохранит свой управляемый PostgreSQL service, но будет вызывать тот же `python -m scripts.run_tests`; CI задаст явный `TEST_DATABASE_URL`. Локально тот же запускатель создаст контейнер. Документация опишет prerequisites, команду, внешний тестовый PostgreSQL и типовые ошибки.

Версия pytest фиксируется в `requirements-dev.txt`, чтобы локальная среда и CI не получали разные версии тестового инструмента при установке.

## Область изменений

- Новый `docker-compose.test.yml` с закреплённым major-образом PostgreSQL, тестовыми credentials, healthcheck и только локально опубликованным портом.
- Новый `scripts/run_tests.py` с двумя режимами: использовать явный URL или временно запустить Compose.
- `requirements-dev.txt` — закрепить версию pytest.
- `tests/postgres_support.py` — требовать только явную тестовую переменную и проверять PostgreSQL URL до подключения.
- `.github/workflows/ci.yml` — вызвать единый тестовый запускатель, не меняя остальные проверки качества.
- Новая инструкция `docs/local-testing.md`, ссылка из `docs/README.md` и обновлённые рабочие инструкции `docs/code-style.md`, `docs/chat-booking-check.md`, `docs/chat-efficiency.md`.
- Тесты запускающего сценария с подменёнными процессами; они не должны требовать PostgreSQL или Docker.

## Ошибки и очистка

- Ошибка запуска Docker/Compose должна содержать команду, которую нужно выполнить, и исходный код возврата.
- Если Compose не готов, запускатель показывает состояние контейнера/ожидания и завершает работу без запуска pytest.
- Очистка контейнера командой `docker compose down --remove-orphans` должна выполняться в `finally` после успеха и после ошибки pytest.
- Явно заданный внешний `TEST_DATABASE_URL` не должен приводить к остановке или удалению внешнего сервера.
- Запуск тестов без явного URL и без работающего Docker должен завершиться до доступа к `.env` и без изменения БД.

## Критерии приёмки

1. `python -m scripts.run_tests` работает локально с Docker и очищает созданный контейнер после завершения.
2. Та же команда использует внешний PostgreSQL только при наличии явного `TEST_DATABASE_URL`.
3. Без переменной и без Docker выводится понятная ошибка; URL из `DATABASE_URL`/`.env` не используется.
4. GitHub Actions использует тот же запускатель и сохраняет все действующие статические и security проверки.
5. Unit-тесты запускателя проходят без PostgreSQL/Docker.
6. Полный набор проходит в доступной тестовой PostgreSQL, включая миграции до head.

## Ограничения

- Этот этап не меняет production-конфигурацию, API, схему приложения или данные.
- Полный результат тестов нельзя считать подтверждённым, пока команда не выполнена против тестовой PostgreSQL.
- Docker Desktop должен быть доступен локально для автоматического режима; без него можно передать отдельный `TEST_DATABASE_URL`.
