# Client authentication and frontend configuration design

## Goal

Make client login behavior and password reset configuration clear, and allow the deployed Vercel frontend to call the API and connect to its existing admin request WebSocket.

## Current project context

`/auth/login` and `/account/login` use the shared `ChatClient` identity. Both currently issue a seven-day access token and there is no refresh-token endpoint. Password reset tokens are hashed in storage and expire after 15 minutes. Reset email links use `FRONTEND_RESET_URL`; if SMTP or the frontend URL is missing, delivery fails. HTTP CORS and chat WebSocket origins are configured separately. The admin request WebSocket uses its own session/origin policy and already exists.

## Design

- Preserve both login routes for compatibility and document that they authenticate the same client accounts. Document their response differences: `/auth/login` returns token fields; `/account/login` additionally returns profile fields. State that access tokens live seven days and no refresh token is currently issued.
- Set the configured reset frontend URL to `https://tours-app-teal.vercel.app/ru/reset-password`; reset links append the encoded token query parameter. Keep the 15-minute expiry and hashed-at-rest behavior. Ensure email failure is visible in logs and API behavior remains non-enumerating for unknown email addresses.
- Add `https://tours-app-teal.vercel.app` to the deployment's HTTP CORS and chat WebSocket allowed origins, using the existing configuration mechanisms. Keep the admin notification socket restricted to the same-origin SQLAdmin page and preserve its session authentication and active-admin check. The Vercel frontend is a client app; it does not need cross-origin access to the admin socket.
- Update `.env.example`, deployment documentation, and API documentation to describe these values and the existing admin WebSocket path and authentication requirement.
- Do not change backend hostname or TLS setup in this scope. Production currently serves a Let’s Encrypt certificate for the IP address, but a custom API hostname requires a domain controlled by the user and DNS pointing to the server. Disk exhaustion currently prevents reliable certificate renewal; resolve disk capacity before deployment.

## Validation and risks

Do not log reset tokens or credentials. Verify origin matching uses exact origins without path components. Configuration changes must not broaden access to arbitrary origins. Confirm the reset URL generated by the mail builder includes `/ru/reset-password?token=...`. Live SMTP delivery requires valid production SMTP settings and cannot be asserted from configuration alone.

## Verification

Add tests first for reset URL construction, token expiry contract, shared login identity/response contract, and allowed-origin handling. Run relevant tests and inspect generated OpenAPI. Do not change production configuration until disk has safe headroom and the database has a verified backup.
