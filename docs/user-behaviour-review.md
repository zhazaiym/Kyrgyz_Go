# Проверка пользовательских сценариев — 2026-10-27

> Исторический отчёт до исправлений. Перечисленные ниже девять дефектов
> исправлены и покрыты регрессионными проверками. Актуальные результаты,
> открытый дефект ИИ и ограничения проверки: [полная диагностика](full-project-audit.md).

Проверен текущий рабочий код после перехода на PostgreSQL и исправления первых
четырёх ошибок. Штатный набор: **283 теста прошли**, полный lint и `git diff
--check` проходят. Дополнительно выполнены сценарии API во временной
PostgreSQL-базе. Рабочая база и код приложения в ходе этой проверки не менялись.

Фронтенда в репозитории нет: это проверка поведения backend/API, а не интерфейса
в браузере. Ответы AI подменялись детерминированными значениями; реальные Gemini
и SMTP не вызывались. Для проверки валидации бронирования также использовались
контролируемые состояния беседы, допустимые текущей схемой извлечения данных.

## Подтверждённые ошибки

### 1. P1 — срок токена зависит от часового пояса PostgreSQL

`client_by_token` заменяет часовой пояс даты на UTC через `replace`, вместо
сравнения существующих aware datetime. PostgreSQL возвращает `timestamptz`
с часовым поясом текущей сессии.

Проверено на одной и той же логике с разными часовыми поясами соединения:

| Часовой пояс | Срок токена | Результат |
|---|---|---|
| UTC | истёк минуту назад | 401, правильно |
| Asia/Bishkek | истёк минуту назад | 200, ошибка |
| America/New_York | действует ещё час | 401, ошибка |

Таким образом, в положительном часовом поясе токен может работать после
истечения срока, а в отрицательном — переставать работать раньше срока.
В текущем локальном окружении авторизация с только что истёкшим токеном
также вернула 200.

Код: [client_auth.py:116](../mysite/api/client_auth.py#L116).
Решение: сохранить offset существующей даты, подставлять UTC только для naive
datetime; добавить тесты с разными часовыми поясами PostgreSQL.

### 2. P2 — обход закрытых полей тура через категории

`GET /tours/{id}/` без входа возвращает 401, а публичный
`GET /tours/category/{category_id}/` возвращает `description`, `included`,
`excluded` и остальные поля полной схемы. Это обходит действующий контракт
«гостю — краткая карточка, подробности — после входа».

Код: [tour.py:388](../mysite/api/tour.py#L388).
Решение: возвращать карточки в публичном маршруте категории либо требовать
клиентский токен для полной выдачи. Публичные описания слайдов главной страницы
следует рассматривать отдельно: они могут быть намеренной частью лендинга.

### 3. P2 — фильтрация и пагинация туров не подключены

Для двух туров с ценами 10 и 100 каждый из запросов вернул оба тура:

```text
GET /tours/?price__lte=1
GET /tours/?search=no-such-tour
GET /tours/?limit=1
```

`TourFilter` существует, но `list_tours` принимает только язык и соединение.
Пользовательские параметры молча игнорируются.

Код: [tour.py:167](../mysite/api/tour.py#L167).
Решение: подключить общий фильтр и пагинацию с сохранением схемы коротких карточек.

### 4. P2 — поиск не учитывает выбранный язык

У отеля есть английское имя `Translated Mountain Lodge`. Запрос с `lang=en`
показывает это имя, но `GET /hotels/?lang=en&search=Translated%20Mountain`
возвращает пустой список. Поиск выполняется по исходным полям, а локализация —
после получения записей.

Код: [filter.py:108](../mysite/filters/filter.py#L108),
[filter_utils.py:20](../mysite/api/filter_utils.py#L20).
Решение: искать по отображаемым переведённым полям с тем же fallback,
который используется при выдаче. Общий механизм нужен и другим локализованным
разделам каталога.

### 5. P2 — исправления после отправки расходятся с сохранённой заявкой

После подтверждения извлечённое исправление имени сохраняется в состоянии
беседы. При этом:

- стадия остаётся `submitted`;
- имя в `TravelRequest` остаётся прежним;
- повторное подтверждение новой ревизии возвращает 409;
- новая сводка не формируется, если извлечение не установило новый
  `booking_intent`.

Код: [chat_service.py:157](../mysite/api/chat_service.py#L157).
Решение: явно определить исправление отправленной заявки. Либо изменения
создают отдельный черновик с новой сводкой, либо сервер сообщает, что нужно
обратиться к менеджеру, и не меняет состояние отправленной версии молча.

### 6. P2 — статус заявки и статус в кабинете расходятся

После успешной заявки подборка имеет `in_progress`. Изменение менеджером
`TravelRequest.status` на `completed` через API возвращает 200, но клиентский
`GET /travel-selections/{id}/` продолжает показывать `in_progress`.
Панель SQLAdmin также редактирует статус заявки отдельно от подборки.

Код: [travel_request.py:50](../mysite/api/travel_request.py#L50),
[manager_selection.py:88](../mysite/api/manager_selection.py#L88),
[views.py:284](../mysite/admin/views.py#L284).
Решение: определить единый статус обработки либо явно различить статус заявки
и статус поездки в контракте. Если кабинет показывает обработку заявки,
он должен читать её актуальный статус; отдельные маршруты и SQLAdmin должны
использовать общую операцию перехода статуса.

### 7. P2 — email в данных беседы не проверяется перед отправкой

Схема `Changes` принимает произвольную строку email, а `build_preview`
не проверяет её формат и длину. Проверены два контролируемых состояния:

| Email | `can_confirm` | Подтверждение |
|---|---|---|
| `not-an-email` | true | 200, некорректный адрес сохранён |
| строка длиннее 255 символов | true | 500 из-за ограничения PostgreSQL |

Код: [agent.py:65](../mysite/chain/agent.py#L65),
[chat_service.py:226](../mysite/api/chat_service.py#L226).
Решение: валидировать необязательный email и в извлечении, и на серверной
границе подтверждения. Не полагаться на инструкцию AI как на проверку данных.

### 8. P2 — некорректный тип WebSocket-токена вызывает исключение

Отправка первого сообщения `{"type":"auth","token":123}` вызывает
`AttributeError: 'int' object has no attribute 'encode'` вместо штатной ошибки
авторизации. Поле передаётся в хеширование без проверки типа.

Код: [chat_ws.py:62](../mysite/api/chat_ws.py#L62),
[client_auth.py:20](../mysite/api/client_auth.py#L20).
Решение: валидировать первое сообщение и ограничить тип/длину токена до доступа
к базе; возвращать управляемую ошибку и закрывать соединение.

### 9. P3 — некоторые параметры списка дают 500 вместо ошибки валидации

Подтверждены:

```text
GET /hotels/?order_by=translations  -> 500 (у JSON нет подходящей сортировки)
GET /hotels/?offset=9223372036854775808 -> 500 (переполнение bigint)
```

Обычная фильтрация по цене, сортировка по цене, отрицательный limit и неверный
диапазон цены обработаны правильно. Проблема касается допустимых полей
сортировки и верхней границы offset.

Код: [filter.py:31](../mysite/filters/filter.py#L31),
[filter_utils.py:8](../mysite/api/filter_utils.py#L8).
Решение: белый список скалярных сортируемых полей и разумная верхняя граница
пагинации; некорректные параметры должны возвращать 422.

## Сценарии без обнаруженных ошибок

- Чужие подборки, их изменение и запуск чата: 404.
- Чужие история беседы, preview и подтверждение: 404.
- Доступ клиента к менеджерскому API: 401.
- Личный список не показывает подборки другого пользователя.
- Пустая подборка отклоняется с 422; неактивная услуга — с 404.
- Повторный запуск подборки возвращает ту же беседу.
- Явный отказ перед подтверждением не создаёт заявку.
- Повторное подтверждение возвращает тот же номер заявки.
- Снимок выбранных услуг доступен менеджеру.
- Пустое сообщение WebSocket получает `invalid_message`.
- Выход отзывает токен: последующий `/auth/me` возвращает 401.

## Ограничения пользовательского пути

После открытия чата PATCH подборки намеренно возвращает 409 с предложением
создать новую поездку. При этом схема AI и промпт не разрешают менять/очищать
`hotel_id` и `transport_id`. Поэтому убрать или заменить выбранную гостиницу
внутри текущей беседы нельзя. Это ограничение уже заложено в контракт; нужно
решить, достаточно ли пользователю пути через новую подборку или нужен явный
сценарий изменения выбранных услуг.

Скрипт воспроизведения и JSON с фактическими результатами сохранены локально
в `backups/user-behaviour-audit.py` и `backups/user-behaviour-audit-results.json`.
