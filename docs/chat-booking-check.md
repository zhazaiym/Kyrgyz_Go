# Проверка заявки из AI-чата

Изменения также развёрнуты на сервере в релизе `20261023-auth-chat-6c3844`. Для проверки используйте локальный адрес или `https://13.53.40.37`.

## Сценарий разговора

1. Запустите backend с настроенной базой и Gemini: `python -m uvicorn main:app --reload`.
2. Откройте чат через существующий frontend. Используйте общий аккаунт `/auth`: токен после входа из detail подходит и чату, отдельная регистрация не требуется. Контракт описан в `docs/shared-client-auth.md`.
3. Попросите подобрать тур. Названия и цены должны поступать из активного каталога.
4. После выбора спросите о размещении. AI использует доступные отели; пожелания о жилье сохраняет в `notes`.
5. Напишите: «Давай забронировать».
6. Сообщите имя, телефон, точную будущую дату и количество людей. Если выбранного тура нет, укажите направление.
7. Backend должен показать сводку и спросить: «Подтверждаете отправку заявки менеджеру?».
8. До подтверждения новая заявка в админке отсутствует.
9. Ответьте «Нет»: заявка не отправляется, данные остаются для исправления.
10. Уточните данные, получите новую сводку и ответьте «Я готова бронировать тур» или «Я готов бронировать тур».
11. Чат возвращает номер созданной заявки. Это запрос менеджеру, а не окончательное бронирование.
12. Войдите как администратор в `/admin/` и откройте «Заявки из чата» (`/admin/chat-request/list`).
13. Откройте заявку: проверьте контакты, дату, число гостей, направление и примечание с туром, бюджетом и пожеланиями.
14. Измените статус обработки через редактирование заявки. В админке оставлен только раздел «Заявки из чата»; старые записи вне чата сохранены в базе, но в этом разделе не показываются.
15. Повторное подтверждение той же заявки возвращает прежний номер и не создаёт дубликат.

## Контракт подтверждения

- `POST /chat/session`: создание диалога с общим Bearer-токеном клиента из `/auth/register` или `/auth/login`.
- `WS /ws/chat/{session_id}`: первое сообщение `{"type":"auth","token":"..."}`; далее `{"type":"message","message":"..."}`.
- WebSocket требует `Origin` из `CHAT_ALLOWED_ORIGINS`.
- При готовой заявке приходит `booking_preview` с `revision`, `data`, `missing_fields` и `can_confirm`.
- `POST /booking/confirm`: тело `{"session_id":"...","revision":1,"confirmed":true}`; Bearer-токен того же клиента.
- `confirmed=false` не отправляет заявку и возвращает HTTP 400. Отказ в переписке переводит диалог в `collecting` и увеличивает `revision`.
- Если выбранный отель или транспорт стал недоступен, его можно удалить из заявки. Если после удаления обязательные данные собраны, API сразу показывает обновлённую сводку и переводит сессию в `awaiting_confirmation`; иначе остаётся в `collecting`.
- При устаревшей `revision` или отсутствии ожидаемого подтверждения возвращается HTTP 409.
- Неполные или некорректные данные нельзя подтвердить; проверка выполняется на сервере повторно перед записью.
- Короткое «да» не отправляет заявку. Явная фраза «Я готова бронировать тур» принимается после сформированной сводки в `awaiting_confirmation`.
- Фразы с исправлениями, например «да, но нас трое», не считаются простым подтверждением и идут на обработку данных.
- После успешной записи приходит `booking_submitted` с `request_id`; повтор возвращает `already_submitted`.
- После подтверждения текст чата: «Ваши данные переданы менеджеру KYRGYZGO. Он скоро свяжется с вами для уточнения деталей и подтверждения бронирования. Номер заявки: …». Сообщение означает сохранение заявки в админке, а не отправку отдельного письма менеджеру и не гарантированную бронь.
- `POST /bookings/` и `POST /travel-requests/` больше не создают заявки: возвращают HTTP 410, `detail.code=booking_requires_chat` и `detail.chat_session_url=/chat/session`. Они скрыты из OpenAPI. Старые защищённые административные операции над историческими записями сохранены.
- Кнопка «Бронировать» на frontend должна открывать чат и передавать выбранный тур первым сообщением. Backend не может самостоятельно открыть окно чата в браузере.
- Сводка, отказ и подтверждение отправки backend поддерживают ru/ky/en/de/zh. Язык хранится в состоянии диалога; другие языки AI может использовать в консультации, а служебные сообщения для них выдаются на английском. Общие технические ошибки могут оставаться на русском.

## Автоматические проверки

`python -B -m pytest tests/test_chat_booking_flow.py tests/test_chat_only_requests.py tests/test_shared_client_access.py -q`

Тесты используют отдельную временную PostgreSQL-базу и подменяют ответы AI. Они проверяют обработку подтверждений и админку, но не оценивают качество реальных ответов Gemini.

## Ручная проверка без frontend через Postman

Инструкция ниже использует локальный backend. Чтобы проверить сервер, замените `http://127.0.0.1:8000` на `https://13.53.40.37`, а WebSocket-адрес — на `wss://13.53.40.37/ws/chat/<session_id>`. Используйте разрешённый сервером `Origin`. Для проверки работающего сервера не нужно устанавливать зависимости или запускать локальное приложение.

1. Установите зависимости: `python -m pip install -r requirements.txt`. Примените миграции: `python -m alembic upgrade head`.
2. Запустите `python -m uvicorn main:app --host 127.0.0.1 --port 8000`. Для реальных ответов нужен действующий `GEMINI_API_KEY` в локальном `.env`.
3. В Postman отправьте `POST http://127.0.0.1:8000/auth/register`, Body → raw → JSON:

```json
{"username":"booking_check","email":"booking.check@example.com","password":"StrongPassword123!"}
```

4. Сохраните `access_token`. Если аккаунт уже зарегистрирован, используйте `/auth/login` с email или логином и паролем. Не отправляйте свой пароль или токен в переписку чата.
5. Отправьте `POST http://127.0.0.1:8000/chat/session` с заголовком `Authorization: Bearer <access_token>`. Сохраните `session_id`.
6. Создайте в Postman WebSocket-запрос к `ws://127.0.0.1:8000/ws/chat/<session_id>`. До подключения добавьте заголовок `Origin: http://localhost:3000` (или другое значение из `CHAT_ALLOWED_ORIGINS`).
7. Подключитесь и отправьте первым сообщением:

```json
{"type":"auth","token":"<access_token>"}
```

8. После события `connected` отправьте сообщение с заведомо тестовыми данными и будущей датой:

```json
{"type":"message","message":"Хочу оставить заявку менеджеру на индивидуальное путешествие. Имя Тестовый Клиент, телефон +996700000001, Каракол, 1 июня 2099 года, на 3 дня, 2 взрослых, бюджет 500 USD, тихое жилье. Покажите сводку и попросите подтверждение."}
```

9. Если AI задаст уточняющий вопрос, ответьте новым сообщением того же формата. Дождитесь `booking_preview` с `can_confirm=true`. В `data` будут собранные поля. До подтверждения заявки в админке быть не должно.
10. Для проверки отказа отправьте `{"type":"message","message":"Нет"}`: заявка не создаётся. Чтобы продолжить, снова попросите показать заявку для отправки и дождитесь нового предварительного просмотра.
11. Для отправки напишите:

```json
{"type":"message","message":"Я готова бронировать тур"}
```

12. Дождитесь `message_delta` с сообщением менеджеру и `booking_submitted` с `request_id`. Откройте `http://127.0.0.1:8000/admin/`, войдите административным аккаунтом, перейдите в «Заявки из чата» и откройте заявку с этим номером.
13. Проверьте имя, телефон, направление, дату, количество гостей, продолжительность и поле сообщения с бюджетом и пожеланиями. Повторите подтверждение — номер должен остаться тем же, без дубликата.

Swagger `/docs` подходит для регистрации и создания сессии, но не предоставляет интерфейс переписки WebSocket. Пароль администратора не совпадает автоматически с паролем клиентского аккаунта.
