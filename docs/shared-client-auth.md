# Единый вход: каталог и чат

Email хранится только в `chat_clients.email`. Регистрация через `/auth/register`
и `/account/register` создаёт одну и ту же клиентскую сущность; повторный email
через любой маршрут отклоняется с HTTP 409. Вход по email и восстановление
пароля работают для обоих способов регистрации. `/account/me` возвращает
email клиента даже при отсутствии заполненного профиля.

Сброс пароля сериализуется блокировкой строки клиента PostgreSQL: из двух
одновременных запросов, включая запросы с разными ссылками одного клиента,
успешен только один. Сброс отзывает токены входа и остальные ссылки.

Запуск чата из подборки возвращает одну беседу даже при одновременных запросах.
Выбранные тур, отель и транспорт показываются в сводке и сохраняются в заявке
как `selected_services` (тип услуги, ID и название на момент подтверждения).
Менеджер получает этот снимок через API заявок; переименование каталога его
не меняет. Подборка после подтверждения получает статус `in_progress`.
Недоступная услуга блокирует подтверждение до изменения выбора.

Один клиентский аккаунт используется для подробных страниц и чата. Отдельная регистрация для чата больше не нужна. Ранее созданные аккаунты и действующие токены сохранены.

## Публичные карточки

Без регистрации доступны GET-списки `/tours/`, `/hotels/`, `/transports/`, `/trekkings/`, `/helicopter-tours/`. Они возвращают краткие карточки с названием, ценой, главным изображением и основными параметрами услуги. Полные описания, условия, программы и контакты в эти карточки не входят.

Детали `/{id}/`, программы и галереи этих объектов требуют общего клиентского Bearer-токена. Создание, изменение и удаление объектов по-прежнему требуют отдельного административного доступа.

## Регистрация и вход

- `POST /auth/register`: `{"username":"customer","email":"guest@example.com","password":"StrongPassword123!"}`. Успех: HTTP 201 и `access_token`. Email необязателен для совместимости со старыми клиентами; при наличии проверяются формат и уникальность без учёта регистра.
- `POST /auth/login`: `{"email":"guest@example.com","password":"StrongPassword123!"}` либо `{"username":"customer","password":"StrongPassword123!"}`. Укажите ровно одно поле идентификатора. Поле `username` также принимает email для единой формы «Email или логин». Успех: HTTP 200 и `access_token`.
- Если аккаунт не найден или пароль неправильный, сервер возвращает одинаковый HTTP 401 с `detail.message`: `Неверный email или пароль`. Новый аккаунт при входе не создаётся.
- Ответы регистрации, входа и `/auth/me` содержат `email` (`null` у старых аккаунтов без почты). Пароли и их хеши не возвращаются.
- Подтверждение владения почтой письмом не реализовано; проверка формата не означает, что почта существует. Email из заявки в чате не используется для входа.
- Перед запуском нового кода выполните `python -m alembic upgrade head`: миграция `20261023_0004` добавляет nullable email и уникальный индекс, сохраняя старые аккаунты.
- `GET /auth/me`: профиль текущего клиента.
- `POST /auth/logout`: отзыв текущего токена; после этого он не открывает ни детали, ни чат.
- Отправляйте один и тот же `Authorization: Bearer <access_token>` в запросах деталей и чата.
- Токен действует семь дней. Вход после истечения срока — повторная авторизация существующего аккаунта, а не новая регистрация.
- Старые `/chat/auth/*` сохранены как скрытые совместимые адреса того же сервиса; они не создают отдельные аккаунты.

## Поведение frontend

1. Показывайте списки без формы входа.
2. При открытии detail или чата используйте общий сохранённый токен.
3. Если токена нет либо сервер вернул HTTP 401, откройте одну общую форму «Регистрация / Вход».
4. Сохраните выбранную detail-страницу или чат как цель возврата.
5. После регистрации либо входа сохраните выданный токен один раз и повторите исходный запрос.
6. При переходе из detail в чат или обратно используйте этот токен, не создавайте новую регистрацию и новый аккаунт.
7. После выхода очистите токен в общем состоянии приложения.

Пример ответа при отсутствии входа:

```json
{
  "detail": {
    "code": "authentication_required",
    "message": "Войдите в аккаунт для доступа к деталям и чату",
    "register_url": "/auth/register",
    "login_url": "/auth/login"
  }
}
```

HTTP 401 является сигналом для интерфейса. Сам backend не открывает модальное окно регистрации. В этом репозитории нет frontend, поэтому отображение формы и хранение общего токена необходимо подключить в клиентском приложении.

## Чат

Создайте диалог через `POST /chat/session` с общим токеном. В WebSocket `/ws/chat/{session_id}` отправьте первым сообщением `{"type":"auth","token":"<access_token>"}`. Для соединения требуется разрешённый `Origin`. История и подтверждение заявки доступны только владельцу диалога.
