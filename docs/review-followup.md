## Применение на сервере и границы проверки

- Общий HTTP-счётчик действует на процесс. Критичные лимиты аккаунтов и чата
  остаются в PostgreSQL и общими для workers. Сетевая DDoS-защита требуется
  отдельно на proxy/провайдере; число workers меняет суммарную HTTP-квоту.
- Docker Compose проверен с профилем https, но Docker daemon локально не
  работает. Контейнерная сеть и боевой трафик на сервере не испытывались.
- При обновлении уже существующей установки нужно применить сетевую
  конфигурацию, а не только новый образ. Текущий CI-deploy сохраняет серверные
  docker-compose.yml и Caddyfile и сам их не заменяет. Сохраните настройки
  боевого PostgreSQL и существующих сервисов при согласовании этих файлов.
- Для host Nginx указывается его фактический peer-IP, видимый Uvicorn;
  фиксированный адрес включённого Caddy не подходит произвольной топологии.
  Если подсеть пересекается с существующей, три proxy-настройки меняются вместе.
- GitHub CI/CD ранее был отключён вручную; включение и деплой этим ревью
  не выполняются. Проверка сайта production не подменяется локальными тестами.
- Снимки SQLite остаются в других ветках/старых клонах. После возможного
  раскрытия боевых данных отдельно нужны смена административного пароля,
  отзыв клиентских токенов и, при необходимости, удаление ссылок/кешей GitHub.
  Реальные аккаунты и токены самостоятельно не изменялись.
- Известное замечание к достоверности предложений ИИ остаётся открытым;
  ограничения агента и пример описаны в `full-project-audit.md`.

Настройка сети основана на [Docker Compose networking](https://docs.docker.com/compose/how-tos/networking/)
и механизме ProxyHeadersMiddleware установленного Uvicorn 0.52.1, который
учитывает заголовки только от явно доверенного peer-IP.
