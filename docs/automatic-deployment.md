# Автообновление сервера из GitHub

## Как работает команда

1. Каждый участник работает в своей ветке и открывает Pull Request в `main`.
2. GitHub Actions проверяет зависимости, Python-код и тесты на отдельной машине без production-секретов.
3. После merge или push в `main`, если проверки успешны, отдельная задача передаёт исходники серверу по SSH.
4. Сервер сохраняет дамп PostgreSQL и прежнюю конфигурацию, собирает образ и перезапускает только backend.
5. После успешного healthcheck и HTTPS-проверки новая версия считается развёрнутой. При ошибке запуска восстанавливается прежний образ через старый override.

Обычным участникам SSH-доступ к серверу не нужен. Не отправляйте изменения напрямую на сервер в обход GitHub: следующий деплой заменит их исходниками из `main`. Защитите `main` правилом Pull Request + обязательная проверка `test`; настройка защиты выполняется владельцем в GitHub Settings.

## Однократная настройка Secrets

Репозиторий: `zhazaiym/Kyrgyz_Go` → Settings → Secrets and variables → Actions → New repository secret.

| Имя | Значение |
| --- | --- |
| `DEPLOY_SSH_KEY` | Полное содержимое `C:\Users\user\.ssh\kyrgyzgo_github_actions_20261023` без расширения `.pub` |
| `DEPLOY_KNOWN_HOSTS` | Полное содержимое `C:\Users\user\.ssh\kyrgyzgo_github_known_hosts` |

Файлы находятся вне репозитория. Не публикуйте приватный ключ в чатах, commit или скриншотах.
Открыть файл можно в текстовом редакторе. Для безопасного копирования сразу в буфер PowerShell:

```powershell
Get-Content "$env:USERPROFILE\.ssh\kyrgyzgo_github_actions_20261023" -Raw | Set-Clipboard
```

После вставки первого секрета скопируйте второй:

```powershell
Get-Content "$env:USERPROFILE\.ssh\kyrgyzgo_github_known_hosts" -Raw | Set-Clipboard
```

После сохранения Secrets откройте Actions → Test and deploy backend. Если предыдущий запуск остановился из-за отсутствия ключа, выберите Re-run failed jobs; либо запустите Run workflow для ветки `main`.
Автообновление нельзя считать включённым до первого успешного запуска задачи `deploy`.

## Серверная часть

- Доверенная точка входа: `/usr/local/lib/kyrgyzgo/ci_deploy.py`, принадлежит root и не обновляется произвольным архивом проекта.
- Для отдельного SSH-ключа настроен forced command; shell, SCP, PTY и перенаправление портов этим ключом запрещены. Разрешён только `deploy <40-значный SHA>`.
- Прежний SSH-доступ разработчика сохранён. Отозвать CI-доступ можно удалением соответствующей публичной строки с комментарием `kyrgyzgo-github-actions` из `~ubuntu/.ssh/authorized_keys` и заменой секрета.
- Релизы: `/home/ubuntu/releases/ci-*`; резервные копии: `/home/ubuntu/kyrgyzgo-backups/ci-*`.
- Последний успешный commit и статус находятся в `deployment-state.json` соответствующей резервной копии.
- Исходный серверный Compose и Caddy не заменяются локальными версиями. Меняется только deployment override.
- `.env`, ключи, локальные базы, тесты и документация не входят в передаваемый runtime-архив. Локальный `kyrgyzgo.db` исключён из новых commit, но история Git не переписывалась.

## Ограничения и безопасность

- На сервере сейчас мало свободного места. Если `Dockerfile` и `requirements.txt` не менялись, используется прежний проверенный runtime и небольшой слой новых исходников. Это сохраняет серверные версии установленных библиотек, а не переустанавливает все зависимости из lock/pin-файла.
- При изменении зависимостей или Dockerfile выполняется полная сборка. Для неё требуется минимум 2 GiB свободного места; иначе деплой завершится ошибкой, а прежнее приложение продолжит работать.
- Даже обычные релизы расходуют место на образы и резервные копии. При свободном месте менее 256 MiB обновление запрещено. Рекомендуется увеличить диск сервера; автоматического удаления старых образов, копий и томов нет.
- Откат образа не отменяет применённые миграции базы. Пишите обратно совместимые миграции. При несовместимой миграции потребуется ручное восстановление из дампа, с учётом новых данных после резервного копирования.
- Участники с правом менять `main` могут запускать production-код. Не выдавайте доступ незнакомым людям. Production-секреты передаются только задаче deploy, не тестам Pull Request.
- Изменение этого доверенного серверного deploy-скрипта требует отдельной установки администратором; обычный push не подменяет forced command.

## Проверка и откат

В GitHub Actions должны быть зелёными обе задачи: `test` и `deploy`. При ошибке смотрите конкретную задачу; успешный push сам по себе не означает успешный деплой.

Для отката выберите нужную резервную копию `ci-*`, восстановите из неё `previous-deploy.override.yml` в `/home/ubuntu/kyrgyzgo-deploy.override.yml`, затем из `/home/ubuntu/Kyrgyz_Go` выполните:

```bash
sudo docker compose up -d --no-deps --no-build --wait backend
```

Не используйте `--build` при откате и не удаляйте PostgreSQL/Caddy volumes.
