# KyrgyzGo API для фронтенда

Контракт кода цикла 8, исходная база `edefb05`. Адрес тестового сервера: `https://13.53.40.37`. Проверяйте фактически выложенный контракт через `GET /openapi.json` и Swagger `/docs`: этот файл сам по себе не означает деплой новых правок.

## 1. Как подключаться

- HTTP API: `https://13.53.40.37`.
- WebSocket: `wss://13.53.40.37/ws/chat/{session_id}`.
- Для JSON-запросов передавайте `Content-Type: application/json`.
- Используйте пути со слешами точно как в таблицах. Редирект из-за пропущенного слеша не должен быть частью обычного сценария.
- Для клиента и администратора есть разные токены. Заголовок одинаковый: `Authorization: Bearer <access_token>`.
- Логин клиента подходит для каталога, подборок и чата. Отдельно регистрироваться в чате не нужно.
- Пароли, токены и серверные ключи не помещайте в URL, аналитику, логи браузера или исходники фронтенда.
- Сервер должен разрешать Origin фронтенда в CORS и отдельно в настройке WebSocket. На 403 при WS проверяйте Origin и принадлежность беседы, а не отключайте проверку Origin.

Обозначения доступа:

| Доступ | Что передавать |
| --- | --- |
| Публичный | Токен не нужен |
| Клиент | Клиентский Bearer-токен |
| Администратор | Административный Bearer-токен |
| Администратор + IP | Административный токен и адрес из allowlist для `/admin` и `/admin/*` |

Отдельной ограниченной роли менеджера пока нет. Менеджерские маршруты используют административный токен, который также даёт права администратора. Название аккаунта `test_manager` не уменьшает его права. Для SQLAdmin есть отдельная cookie-сессия после входа через HTML-форму; Bearer-токен автоматически её не создаёт.

## 2. Основной путь пользователя

1. Без входа показать списки туров, отелей, транспорта, трекингов и вертолётных туров.
2. При открытии полной карточки запросить вход, если нет действующего клиентского токена.
3. Зарегистрировать пользователя через `/auth/register` или `/account/register`, затем использовать один полученный токен везде.
4. Для выбранных тура, отеля и транспорта создать подборку через `POST /travel-selections/`, затем вызвать её `/start-chat/`. Для свободного запроса без подборки вызвать `POST /chat/session`.
5. Подключить WebSocket, отправить токен первым сообщением, затем вести переписку.
6. Показать `booking_preview` и кнопку подтверждения только при `can_confirm=true`. Сохранить `revision` именно этой сводки.
7. По отдельному действию пользователя вызвать `/booking/confirm` с `confirmed=true` и сохранённой revision.
8. Показать `request_id` как номер заявки менеджеру. Это ещё не оплата и не гарантированное бронирование.

Записи с `ТЕСТ:` или `TEST:` можно смотреть в каталоге, но нельзя включать в подборку или подтверждать как настоящую услугу. Текущий демонстрационный каталог предназначен для проверки отображения. Чтобы проверить свободную заявку, можно обсудить направление без выбора демо-тура.

## 3. Вход, регистрация и профиль

`POST /auth/register` принимает `{username, password, email?}`. Username содержит 3-50 символов `a-z`, `0-9`, `_`; пароль 8-128 символов. Email необязателен и нормализуется. Успех 201: `{access_token, token_type, client_id, client_code, username, email}`.

`POST /auth/login` принимает либо `{username, password}`, либо `{email, password}`. Не передавайте username и email одновременно. Поле username также может содержать email. Успех 200 имеет тот же набор полей, что регистрация. Неверные данные дают 401, совпавший логин/email при регистрации даёт 409.

`/account/*` работает с той же учётной записью, но предоставляет форму с именем и телефоном. Регистрация принимает `{name, phone, email, password}` и сама создаёт технический username. Вход принимает `{email, password}`. Ответ дополнен `name` и `phone`; у пользователя, созданного через `/auth/register`, они могут быть null. Два маршрута не создают два независимых аккаунта.

Подтверждения владения email при регистрации нет. Email из заявки менеджеру не считается email учётной записи.

`GET /auth/me` возвращает `{client_id, client_code, username, email}`. `GET /account/me` добавляет имя и телефон. `POST /auth/logout` отзывает переданный клиентский токен, а не все сессии пользователя. После выхода удалите токен на фронтенде и закройте WebSocket.

Восстановление пароля:

- `POST /account/forgot-password` с `{email}` всегда даёт одинаковый ответ `{message}`, если запрос принят. Он не подтверждает наличие пользователя или успешную доставку письма. SMTP и страница восстановления должны быть настроены на сервере.
- Ссылка из письма содержит token и действует 15 минут.
- `POST /account/reset-password` принимает `{token, new_password}`. При успехе возвращает `{ok:true, message}` и отзывает все клиентские токены и остальные ссылки восстановления. Нужно войти заново.
- Неверная, использованная или истёкшая ссылка даёт 400.

Пример входа:

```js
const response = await fetch(`${API_URL}/auth/login`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email, password }),
});
const payload = await response.json();
if (!response.ok) throw payload;
const clientToken = payload.access_token;
```

## 4. Каталог, язык, фильтры и пагинация

`lang=ru|en|de|zh`, по умолчанию `ru`, выбирает язык поддерживающего его GET. Если актуального непустого перевода нет, сервер возвращает исходный текст. Фронтенд не должен скрывать такое поле или самостоятельно подставлять устаревший перевод. Список и поиск используют язык отображения.

Списки с `limit` и `offset` возвращают обычный массив, без общего `total`. По умолчанию limit=100, диапазон 1-100; offset=0, диапазон 0-1000000. Следующую страницу запрашивайте через `offset + limit`; короткая страница означает конец. Для `/chat/sessions` и истории действуют отдельные пределы, описанные ниже.

У пяти основных списков карточки краткие. Полное описание, адреса, условия и программы получайте из защищённых деталей и связанных маршрутов. У тура детали содержат `images` и `programs`; у остальных сущностей галереи и программы доступны отдельными запросами.

Списки каталога возвращают активные услуги. Обновление и создание выполняет администратор. `PUT` в этом API обновляет только присланные поля, поэтому не нужно отправлять весь объект из GET. Пропущенное поле сохраняется, а явный null очищает только поле, где null разрешён схемой. Не передавайте поля карточки или ответа, которых нет во входной схеме.

Для файлов изображений здесь нет upload-endpoint: поля `image` и `main_image` принимают URL, а не File или base64. Сервер может отклонить удаление используемой услуги кодом 409. Для перевода текста не нужно вызывать Gemini с фронтенда: переводы готовит backend после сохранения. Новый перевод может появиться позднее.

Общие фильтры пяти основных каталогов: `price__gte`, `price__lte`, `price_unit`, `search`, `order_by`. Конкретные дополнительные фильтры перечислены у каждого GET в разделе 10. Нижняя граница должна быть не больше верхней.

Сортировка: `order_by=price,-id` означает цену по возрастанию и id по убыванию. Передавайте одну строку со значениями через запятую. JSON, отношения и неизвестные поля сортировки дают 422.

Пример: `GET /tours/?lang=en&country_id=1&guests=2&price__gte=50&price__lte=500&order_by=price&limit=10&offset=0`.

Денежные и координатные Decimal в JSON могут быть строками. Для вычислений явно преобразуйте их, для хранения цены избегайте потери точности. Валюта отдельным полем не возвращается; `price_unit` задаёт единицу расчёта, а не валюту. Даты поездки имеют вид `YYYY-MM-DD`, временные метки - ISO 8601.

## 5. Подборки и кабинет

`POST /travel-selections/` принимает `{tour_id?, hotel_id?, transport_id?}`. Нужна хотя бы одна доступная услуга, id - положительное число. Неактивная, отсутствующая или демонстрационная услуга даёт 404. Пустой набор даёт 422.

Ответ подборки: `{id, client_id, tour_id, tour_name, hotel_id, hotel_name, transport_id, transport_name, session_id, status, request_id, created_at}`. Не выбранные услуги и ещё не созданная заявка имеют null. `request_id` и статус могут меняться после действий менеджера.

`GET /travel-selections/me/` возвращает только подборки текущего клиента. Чужая подборка при GET, PATCH и start-chat даёт 404.

`PATCH /travel-selections/{selection_id}/` меняет только указанные id; null убирает услугу. После появления связанного чата или выхода из draft редактирование даёт 409. Тогда создайте новую подборку; после начала чата отдельно разрешено удалить отель или транспорт через `/chat/{session_id}/services/{kind}`.

`POST /travel-selections/{selection_id}/start-chat/` возвращает `{selection_id, session_id, existing:false, selection_message, welcome}`. Повтор возвращает тот же session_id с `existing:true` и `stage`, без создания новой беседы. Поля selection_message/welcome могут отсутствовать в повторном ответе.

Менеджер читает подборки через `/manager/travel-selections/` и меняет статус через `/{selection_id}/status/`. Ответ дополнен `client_code` и `username` при чтении менеджерского списка/деталей. Не делайте вывод о правах по username.

Статусы подборки: `draft`, `in_progress`, `completed`, `cancelled`. Статусы заявки: `new`, `in_progress`, `completed`, `cancelled`. Завершённый объект нельзя вернуть в другой статус; попытка даёт 409. Подборку со связанным чатом нельзя вернуть в draft. При подтверждении заявки подборка становится in_progress.

## 6. Чат по HTTP и WebSocket

`POST /chat/session` без тела создаёт беседу и возвращает `{session_id, welcome}`. Нужен клиентский токен. Не создавайте новую беседу при каждом reconnect.

`GET /chat/sessions` возвращает максимум 50 последних бесед клиента: `[{session_id, created_at, stage}]`. `GET /chat/history/{session_id}` возвращает максимум 500 последних сообщений в хронологическом порядке: `[{role, content, created_at}]`. Чужая беседа даёт 404.

Подключение и первые сообщения:

```js
const ws = new WebSocket(`${WS_URL}/ws/chat/${sessionId}`);
ws.onopen = () => ws.send(JSON.stringify({ type: 'auth', token: clientToken }));
ws.onmessage = ({ data }) => {
  const event = JSON.parse(data);
  // Отправлять текст можно после события connected.
  handleChatEvent(event);
};
// После connected:
// ws.send(JSON.stringify({ type: 'message', message: 'Хочу поездку в Каракол' }));
```

В браузере Origin устанавливается автоматически. Авторизация WebSocket передаётся первым JSON-кадром, не query-параметром и не произвольным заголовком браузерного WebSocket. У первого кадра вид `{type:"auth", token:"..."}`; его надо отправить в течение 30 секунд. Затем сообщения имеют вид `{type:"message", message:"..."}`, длина текста 1-2000 символов. Бинарные кадры и пустые сообщения не принимаются.

События сервера:

| type | Поля | Действие фронтенда |
| --- | --- | --- |
| `connected` | session_id | Разрешить отправку сообщений |
| `typing` | status: boolean | Показать или убрать индикатор ожидания |
| `message_start` | message_id | Создать временное сообщение ассистента |
| `message_delta` | message_id, delta | Дописать delta к сообщению с этим id |
| `booking_preview` | status, session_id, revision, data, missing_fields, complete, can_confirm | Заменить сводку и сохранить revision |
| `message_end` | message_id, revision, booking_intent, stage | Завершить сообщение и обновить стадию |
| `booking_submitted` | status, request_id, client_code | Показать номер заявки |
| `error` | code, message, иногда retry_after | Показать ошибку и снять ожидание |

Куски message_delta могут прийти после завершения генерации целиком. Индикатор ожидания нужен даже при отсутствии промежуточных кусков. `booking_intent=true` означает намерение, а не факт отправки; факт подтверждается booking_submitted или успешным `/booking/confirm`.

Стадии чата: `consultation`, `collecting`, `awaiting_confirmation`, `submitted`. После submitted данные заявки не меняются сообщениями; для новой поездки нужен новый чат или обращение к менеджеру.

Коды WS-ошибок: `invalid_message`, `authentication_failed`, `session_expired`, `session_not_found`, `booking_conflict`, `request_invalid`, `rate_limited`, `ai_busy`, `ai_timeout`, `ai_rate_limit`, `ai_unavailable`, `internal_error`, `service_unavailable`. При rate_limited учитывайте retry_after. При ошибке авторизации нужно войти заново. Закрытие 1008 означает отказ по политике/протоколу; 1011 - сбой сервиса. После reconnect загрузите историю HTTP-запросом; автоматически повторять действие подтверждения вслепую не нужно.

## 7. Сводка и подтверждение заявки

`POST /booking/preview` принимает `{session_id}` и возвращает:

```json
{
  "status": "draft",
  "session_id": "uuid",
  "revision": 3,
  "data": {
    "client_name": "Тестовый клиент",
    "phone": "+996700000001",
    "email": null,
    "people_count": 2,
    "travel_date": "2030-06-01",
    "destination": "Каракол",
    "selected_services": []
  },
  "missing_fields": [],
  "complete": true,
  "can_confirm": true
}
```

`data` - состояние заявки, состав дополнительных полей может расширяться. `selected_services` содержит `{kind, id, name}`. `complete` говорит о полноте данных, а кнопку разрешает только `can_confirm`. Полная заявка на стадии collecting ещё не готова к подтверждению.

Нужны client_name, корректный phone, people_count, travel_date не в прошлом, а также tour_id или destination. Email и duration_days необязательны, но проверяются, если указаны. При выбранном туре проверяется размер группы. В missing_fields возможны `client_name`, `phone`, `people_count`, `travel_date`, `future_travel_date`, `valid_travel_date`, `tour_or_destination`, `valid_email`, `duration_days`, `valid_tour`, `valid_hotel`, `valid_transport`.

Кнопка подтверждения отправляет:

```json
{"session_id":"uuid","revision":3,"confirmed":true}
```

Нужен клиентский Bearer даже там, где Swagger не рисует замок: `/booking/confirm` и DELETE услуги читают Authorization через отдельную зависимость.

Успех `/booking/confirm`: `{status:"submitted", request_id, client_code}`. Повтор уже выполненного подтверждения: `status:"already_submitted"` с прежним номером, без дубликата. `confirmed:false` даёт 400 и не является endpoint для изменения стадии отказа. Для отказа отправьте сообщение в чат, например `Нет`.

На устаревшую revision/неподходящую стадию приходит 409. Если услуга стала недоступной, detail может содержать `{code:"booking_needs_update", status:"needs_update", answer, revision, stage, booking_preview}`. Обновите сводку и revision из этого ответа, не повторяйте старое подтверждение автоматически.

`DELETE /chat/{session_id}/services/hotel` или `/transport` без тела убирает необязательную услугу и возвращает `{status:"updated", stage, revision, answer, booking_preview}`. Если данных достаточно, сервер сразу выдаёт новую сводку и awaiting_confirmation. После отправки заявки удаление запрещено (409).

Текстовое подтверждение также поддержано, но короткое `да` не отправляет заявку. Надёжный фронтенд использует отдельную кнопку с revision. Текст вроде `Я готова бронировать тур` учитывается только после показанной сводки.

Прямые `POST /bookings/` и `POST /travel-requests/` сняты с использования: 410, `detail.code=booking_requires_chat`, `detail.chat_session_url=/chat/session`. Они не видны в OpenAPI, но фронтенд должен убрать старые формы отправки.

## 8. Ошибки и ограничения

| Код HTTP | Что делать |
| --- | --- |
| 400 | Исправить действие или данные, например недействительную ссылку сброса |
| 401 | Для защищённой страницы запросить вход, затем вернуться к исходному действию |
| 403 | Нет доступа по IP/политике или аккаунт отключён; повторный логин не всегда помогает |
| 404 | Объект отсутствует, недоступен или принадлежит другому клиенту |
| 409 | Состояние изменилось; обновить объект/сводку, не повторять старую операцию автоматически |
| 410 | Старый endpoint выведен из использования; перейти к сценарию чата |
| 413 / 414 / 431 | Уменьшить тело, URL или заголовки запроса |
| 422 | Показать ошибки валидации полей/фильтров |
| 429 | Выдержать Retry-After или retry_after; не запускать цикл повторов |
| 500 / 502 / 503 | Показать временную ошибку, сохранить ввод, предложить повтор позже |

Тело HTTP-ошибки обычно `{detail: ...}`. detail может быть строкой, объектом или массивом Pydantic с `loc`, `msg`, `type`. В ошибке клиентской авторизации это объект с code, message, register_url, login_url. Обрабатывайте все формы, а неизвестный текст показывайте с безопасным общим fallback.

По умолчанию AI ограничен 10 сообщениями в минуту и 300 в сутки на клиента; создание чатов и подборок - 30 в час на клиента. Есть общие IP/ресурсные ограничения. Это серверные настройки, а не числа для клиентского таймера. Уважайте фактически возвращённый Retry-After. Вход и выход не отключают лимиты.

## 9. Дополнительные маршруты и HTML-админка

- `GET /` возвращает `{message:"Welcome to KYRGYZGO API"}`. Это HTTP-проверка доступности, а не проверка Gemini или содержимого каталога.
- `GET /docs`, `GET /redoc` и `GET /openapi.json` предоставляют интерактивную и машиночитаемую документацию.
- `/chat/auth/register`, `/chat/auth/login`, `/chat/auth/me`, `/chat/auth/logout` - совместимые алиасы соответствующих `/auth/*` с теми же методами. Для новой интеграции используйте `/auth/*`.
- `/admin/`, `GET /admin/login`, `POST /admin/login` (form-urlencoded username/password), `GET /admin/logout`, а также страницы списков/создания/редактирования/деталей SQLAdmin - HTML-интерфейс. Они используют cookie и IP-allowlist. Не путайте форму `/admin/login` с JSON API `POST /admin/login/`.
- Подсказка для SQLAdmin: чтобы очистить перевод и запросить автоматический перевод, задайте конкретному полю пустую строку. Отсутствующий ключ в JSON сохраняет текущее значение. Не редактируйте служебные `_source_hashes` и `_manual_fields`.

## 10. Все HTTP endpoint

Здесь перечислены все JSON-маршруты из OpenAPI. Схемы входа и ответа расшифрованы в разделе 11. Схема `Тип[]` означает массив, `null` - допустимое пустое значение. У каждого endpoint приведены его собственные параметры; отсутствие параметра в списке означает, что на него не нужно рассчитывать.

## 12. Проверка интеграции перед выпуском фронтенда

- Гость видит карточки, а полная карточка без входа даёт 401 и открывает общий экран входа.
- После входа тот же токен открывает детали, подборки и WebSocket.
- Список с фильтрами использует фактический lang и корректный offset; пустая выдача не заменяется выдуманными предложениями.
- Демо-услуга не считается доступной для бронирования.
- Чужая подборка/беседа корректно обрабатывается как 404.
- На collecting кнопка подтверждения неактивна, даже если complete=true.
- При новом preview старая revision заменяется, а старое подтверждение не отправляется повторно.
- При 409 booking_needs_update пользователь видит новую сводку и недоступную услугу.
- Повтор подтверждения показывает тот же request_id.
- После logout закрывается WebSocket, клиентский токен удаляется.
- Ошибка/таймаут AI завершает индикатор ожидания и не отображается как успешный ответ.
- Менеджерский токен не попадает в публичный клиентский bundle.
